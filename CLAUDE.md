# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BLEScanner is a native iOS 18.6+ app for scanning BLE devices and iBeacons, connecting to them,
and reading/writing GATT characteristics. It's a central-role (client) app only — no
peripheral/advertising mode. See `docs/specification.md` for the full product spec, including
the deliberate deviations from the Android reference app whose screenshots live in
`android_images/` (e.g. no MAC addresses on iOS — filtering uses `CBPeripheral.identifier`
instead, exposed as "By Identifier").

## Repository layout

```
BLEKit/                  Local SPM package — ALL logic and TCA reducers live here
  Sources/BLEKitCore/         Pure models/parsing/classification — zero Apple-framework imports beyond Foundation
  Sources/BLEKitHardware/     CoreBluetooth/CoreLocation → AsyncStream bridges
  Sources/BLEKitDependencies/ swift-dependencies DI clients, SwiftData History, @Shared keys
  Sources/BLEFeatures/        TCA reducers (this is the app's actual business logic)
  Sources/BLEKitTestSupport/  Fixtures + fakes, used by package tests AND the app's -UITesting path
  Tests/                      Swift Testing + TCA TestStore + SwiftData integration tests
BLEScanner/               Xcode project — deliberately thin (entry point + SwiftUI views only)
  project.yml                 xcodegen source of truth — DO NOT hand-edit BLEScanner.xcodeproj
  BLEScanner/                 App target sources (Views/, UITestSupport/, Extensions/)
  BLEScannerUITests/          XCUITest smoke suite
docs/specification.md    Full product specification
android_images/          Android reference app screenshots (non-code, for context only)
```

## Commands

### BLEKit package (do this first when changing any logic/reducer)

```bash
cd BLEKit
swift build
swift test                                    # full suite (60 tests)
swift test --filter ScannerFeatureTests       # single suite
swift test --filter <SuiteName>/<testMethod>  # single test
```

### Xcode app

The `.xcodeproj` is generated by `xcodegen` from `project.yml`. After editing `project.yml` or
adding/removing/moving files under `BLEScanner/BLEScanner/` or `BLEScanner/BLEScannerUITests/`,
regenerate before building:

```bash
cd BLEScanner
xcodegen generate
```

Building/testing from the CLI requires `-skipMacroValidation -skipPackagePluginValidation`
(macro trust prompts otherwise block non-interactive builds):

```bash
xcodebuild -project BLEScanner.xcodeproj -scheme BLEScanner \
  -destination 'generic/platform=iOS Simulator' -configuration Debug \
  -skipMacroValidation -skipPackagePluginValidation build

# UI tests need a concrete simulator id (list with: xcrun simctl list devices available)
xcodebuild -project BLEScanner.xcodeproj -scheme BLEScanner \
  -destination 'platform=iOS Simulator,id=<UDID>' \
  -skipMacroValidation -skipPackagePluginValidation \
  test -only-testing:BLEScannerUITests
```

Deployment target is iOS 18.6, set via `IPHONEOS_DEPLOYMENT_TARGET`/`deploymentTarget` in
`project.yml`. `BLEKit/Package.swift` stays at `.iOS(.v18)` — SPM's `platforms:` only supports
whole major-version floors, no minor-version granularity — the real 18.6 floor is enforced by
the Xcode project setting, not the package manifest.

## Architecture

**TCA (The Composable Architecture) + Swift 6.3 strict concurrency**, deliberately chosen for
this project even though the developer's other repos use plain SwiftUI `@Observable` — don't
"fix" this repo to match that convention.

### Reducer tree

`AppFeature` (root: `NavigationSplitView` sidebar selection) scopes into `ScannerFeature`,
`FilterFeature`, `SettingsFeature`. `ScannerFeature` further scopes a nested `HistoryFeature`
(the Scanner screen's "History" tab, not a sidebar item) and presents `DeviceDetailFeature` via
`@Presents`/`PresentationAction` when a device row is tapped. `SettingsFeature` presents
`AddKnownBeaconFeature` the same way for its "Add Known Beacon" sheet.

### Hardware layer (`BLEKitHardware`)

`LiveBLECentralManager`, `LiveBLEPeripheralConnection`, `LiveBeaconRanging` are **not**
`@MainActor`. They're plain `NSObject` subclasses marked `@unchecked Sendable`, confining all
mutable state and delegate callbacks to one dedicated serial `DispatchQueue` (passed as both the
CoreBluetooth delegate queue and the queue every public method dispatches onto). This was a
deliberate choice over `@MainActor`: marking these classes `@MainActor` breaks two things —
`CBCentralManagerDelegate`/`CLLocationManagerDelegate` conformance needs `extension Foo:
@MainActor SomeDelegate` isolated-conformance syntax in Swift 6.3, and constructing a
`@MainActor` type inside a static `DependencyKey.liveValue` (which isn't actor-isolated) doesn't
work cleanly. `LiveBeaconRanging` specifically creates its `CLLocationManager` on the main thread
(required for delegate callbacks to fire) but isn't itself `@MainActor`.

`GATTIdentifier` (in `BLEKitCore`) wraps `CBUUID` as a plain uppercased string precisely so
`BLEKitCore` never has to import CoreBluetooth. `BLEKitHardware` converts to/from `CBUUID` at
its boundary.

`PeripheralConnectionClient` (in `BLEKitDependencies`) is a `Sendable` struct of closures wrapping
a `BLEPeripheralConnection`, vended per-identifier by `BluetoothScannerClient.makeConnection`. The
live implementation (`LiveBLECentralManager.makeConnection`) caches one connection per identifier
— reducers call `makeConnection` again on every subsequent operation (read/write/notify/discover)
rather than holding onto the connection object, relying on that caching. The `-UITesting` fake
(`AutopilotConnectionCache` in the app target) replicates this caching; a version without it
silently breaks GATT discovery because `discoverServices()` ends up called on a fresh,
unsubscribed instance. Watch for this if you touch fake/live connection-vending code.

### Persistence

`@Shared(.appStorage(...))` (via `SharedKeys.swift`) for `FilterCriteria`, `AppSettings`,
`[KnownBeacon]`. SwiftData (`HistoryRecord` + `HistoryModelActor`, a `@ModelActor`) is used only
for scan History — `@Model` types aren't `Sendable`, so the actor returns plain `Sendable`
`HistoryRecordDTO` values across the boundary; views never use `@Query` directly.

`KnownBeacon.id` derives from `uuid` (`var id: UUID { uuid }`) rather than being independently
generated, since only one registration per beacon UUID is ever allowed — this also makes
`TestStore` assertions on appended `KnownBeacon` values deterministic. Similarly, reducers that
construct timestamped values inject `@Dependency(\.date.now)` instead of calling `Date.now`
directly, for the same reason.

### TCA gotchas hit in this codebase (worth knowing before writing new reducer code)

- **`TestStore` requires an explicit `.receive()` to actually apply an effect-produced action to
  state** — even in non-exhaustive mode. A `.run` effect's `send(...)` genuinely doesn't mutate
  `store.state` until you `.receive()` it in the test.
- **Bare `Effect.send(...)` through a `.ifLet`/presentation boundary has non-deterministic timing
  in `TestStore`** (observed to sometimes resolve synchronously within the originating `send`,
  sometimes as a separately-queued action, seemingly depending on scheduling/parallel test
  execution). `AddKnownBeaconFeature`'s delegate actions use `.run { send in await send(...) }`
  instead of bare `.send(...)` specifically to route through the well-defined async effect
  machinery and avoid this. Prefer `.run { send in await send(...) }` for delegate-style actions
  crossing a presentation boundary.
- **`@Shared` test isolation**: override `$0.defaultAppStorage = .inMemory` in a test's
  `withDependencies` block when the test touches `@Shared(.appStorage(...))` state (filter
  criteria, settings, known beacons) to guarantee isolation from other concurrently-running
  tests, rather than relying on the library's automatic per-test provisioning.

### NavigationSplitView / SwiftUI landmines

- The sidebar in `RootView` **must** use `List(SidebarDestination.allCases, selection:
  sidebarSelectionBinding)` — i.e. drive the actual `List(selection:)` binding. Replacing it with
  a `ForEach` of plain `Button`s that only dispatch a TCA action (a real regression that shipped
  once) breaks `NavigationSplitView`'s automatic sidebar→detail push on compact width (iPhone):
  the split view only learns a new destination was picked via its own tracked selection binding,
  not via arbitrary state changes elsewhere. It "worked" on iPad only because both columns are
  already visible there, masking the bug.
- `SwiftUI Toggle` inside `Form` was found to not reliably respond to XCUITest-synthesized taps
  on some Xcode/iOS Simulator combinations (confirmed via app-level debug prints that the
  `Binding`'s `set` closure never fired despite the tap reporting success) — this is a
  Simulator/automation limitation, not an app bug; the underlying logic is covered by
  `FilterFeatureTests`/`DeviceFilterTests` via `TestStore` instead. `BLEScannerUITests`
  intentionally checks Filter-screen structure rather than driving that toggle.

### `-UITesting` launch path

`BLEScannerApp.swift` checks `ProcessInfo.processInfo.arguments.contains("-UITesting")` (Debug
builds only, `#if DEBUG`) and, if present, overrides dependencies with fakes from
`BLEKitTestSupport` plus the app-target-local `UITestSupport/` (seeded fixture devices/history,
`AutopilotConnectionCache` for self-driving GATT connect/discover/read flows) — the Simulator has
no real Bluetooth radio, so this is how `BLEScannerUITests` exercises real UI flows end-to-end.
